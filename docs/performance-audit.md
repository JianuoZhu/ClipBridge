# 延迟与预览性能排查

检查日期：2026-09-08。依据为当前工作区代码、部署模板、隔离本地测试和相关官方文档。当前 `.env` 的域名是 `localhost`，尚未取得生产域名、两端链路测速或生产监控，因此不能把公网服务器带宽判定为已经实测确认的唯一根因。本次没有修改业务代码或生产部署。

## 结论

按仓库模板部署时，所有站点业务流量都会走公网入口：

```text
浏览器 → 公网 HAProxy → WireGuard → 家中 Caddy → Node.js / SQLite / 文件
```

中转者是公网服务器，不是浏览器。`infra/server/haproxy.cfg` 的 `mode tcp` 和 `home_https` 后端把整个 HTTPS 连接交给家中节点，没有区分消息、小图或下载的直连通道。TLS 也在家中终止。

如果国内公网入口的出口带宽很小，它会限制下载和预览；家中上传带宽、两端线路质量及客户端网络同样可能成为瓶颈。尤其当家中节点或访问者在海外时，绕行和丢包需要单独验证，不能仅按服务器所在地判断性能。

空闲时发送几百字仍要数秒，不能仅用“小带宽”解释；应继续查往返延迟、丢包、请求排队、消息列表体积和家中磁盘。下载过程中才显著变慢，则更符合共享带宽拥塞的表现。

## 已确认的应用问题

| 问题 | 代码依据 | 对体验的影响 | 解决方式 |
| --- | --- | --- | --- |
| 图片缩略图返回原文件 | `web/src/components/Thumbnail.tsx` 给 `/preview` 加 `thumbnail` 参数；`src/server.js` 不处理这个参数，直接流式返回原文件 | 看小图也需要传大图；多张图同时占用消息与下载的链路 | 在家中异步生成真正的小图，独立鉴权接口返回；例如最长边 320 像素，目标几十 KiB，原图仅在打开预览时加载 |
| 发送完成依赖列表刷新 | `web/src/hooks/useClipBridge.ts` 的 `sendText` 丢弃 POST 返回的 item，随后 `await loadItems()` | 服务端已保存，发送按钮仍在等额外网络请求 | POST 成功后用返回 item 更新当前列表和最新文字，立即确认；背景刷新用于校准，处理好删除、登出和并发响应竞态 |
| 每次通知重新拉完整列表 | SSE 只含 action/itemId；客户端等待 120 ms 后 GET `/api/items`，返回最多 100 条完整正文及 latest | 接收新消息额外需要列表请求；历史正文多时放大传输与解析成本；发送端的主动刷新和 SSE 也可能触发连续刷新 | 事件携带必要增量，或按 ID 补取；重连时才完整校准。去重并合并刷新；将持续重置的 debounce 改成有最大等待时间的合并机制 |
| PDF 缩略图在客户端生成 | `web/src/lib/thumbnails.ts` 自动加载 20 MiB 内 PDF，并导入 PDF.js/worker；并发上限为 2 | 显示文件卡片就可能发起多个 Range 请求并下载解析器；高 RTT 时慢，弱设备还要解析渲染 | 家中异步预生成 PDF 第一页小图；生成期间显示文件图标，任务并发受控且不阻塞上传完成或 Node 事件循环 |
| PDF 任务依赖不稳定对象 | `Thumbnail` effect 依赖整个 `file` 对象，`App.tsx` 的 `toPreview()` 每次渲染创建新对象 | 上传进度、消息刷新等父组件更新可取消并重启尚未完成的小图任务 | 依赖 scope/id/revision/size/type/session 等稳定字段；同一资源共享正在运行的任务，保持登出取消机制 |
| 预览不复用文件响应 | 预览/下载均返回 `private, no-store`；小图与弹窗 URL 还不同 | 点开图片通常需要新请求；PDF 小图内存缓存不等于文档缓存 | 优先减少响应体积；需要复用时采用受限的会话内存缓存，登出、删除、修订时清理，不直接给私有文件加公共缓存 |

文件下载已经使用流式读取，支持单区间 Range，没有发现业务代码人为限制下载带宽。提高 Node 超时、盲目增加并发或只换成 WebSocket，并不能解决带宽上限和原图缩略图问题。

SSE 在保存后直接写出，不依赖心跳才发送。Caddy 官方说明 `text/event-stream` 会立即刷新，因此目前没有依据把问题归咎于“Caddy 默认攒住 SSE”；如果实际还有其他代理，应实测该路径。[Caddy streaming 文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#streaming)

PDF 已启用 Range，并关闭自动预取及流式整文件读取。未配置 `rangeChunkSize`，当前依赖和官方默认值为 65536 字节；多个相互依赖的范围请求会受到 RTT 影响，但不代表每份 PDF 都按固定顺序读取整个文件。可比较 64/256/512 KiB 的首页时间与实际下载字节，再选择参数；增大范围也可能多下载无用内容。[PDF.js 参数文档](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html)

## 本地验证

使用临时目录、独立 SQLite、回环 HTTP 和合成数据，无生产用户数据；完成后关闭服务并删除该临时目录。

| 检查 | 结果 |
| --- | --- |
| 30 次短文字 POST，含 HTTP 请求与读取响应 | 中位数 1.19 ms，95 分位 2.33 ms |
| 30 条短文字列表 | 1.45 ms，4910 字节 |
| 2 MiB PNG 签名合成文件请求 `preview?thumbnail=0` | 返回 2097152 字节，与上传内容逐字节相同；测试验证接口传输行为，不验证图片解码 |
| 请求该文件 `Range: bytes=0-65535` | 206，65536 字节 |
| 100 条、每条 256 KiB 的合成正文列表 | 响应 26490501 字节，本地约 172.48 ms |

这些数字不是线上性能指标，也不能排除家中磁盘较慢。大列表测试使用高度可压缩的合成文字且未经过 Caddy；上述字节数是未压缩响应大小，不能当作生产实际流量。它说明当前协议会重复返回全部正文。

带宽容量的简单估算：10 MiB 文件经过独占的 5 Mbps 瓶颈，理想传输时间约 `10 × 1024 × 1024 × 8 / 5000000 = 16.8 秒`；1 Mbps 约 83.9 秒。真实链路还要加协议开销、竞争和重传。如果小图只有 50 KiB，同样 5 Mbps 下纯传输时间约 0.082 秒，仍需加 RTT。

## 线上如何定位具体哪一段慢

使用同一个小接口和同一个测试文件，分别在空闲、上传中、下载中测量。重复 10–20 次，比较中位数、尾延迟、吞吐，区分首次握手和连接复用；小接口测试不能代替大文件吞吐测试。

1. **家中应用自身**：在家中执行以下命令，验证服务和数据库读取的本地响应；写入延迟另用测试文字测量。

   ```bash
   sudo docker compose exec clip node -e "const t=performance.now();fetch('http://127.0.0.1:8080/healthz').then(async r=>{await r.text();console.log({status:r.status,ms:performance.now()-t})})"
   ```

2. **公网入口到家中**：在公网服务器上绕过 HAProxy，访问隧道内 Caddy，保留真实域名及 TLS 校验。把 `clip.example.com` 换成实际域名。

   ```bash
   curl --resolve clip.example.com:443:10.66.0.2 --connect-timeout 5 --max-time 15 -sS -o /dev/null -w 'code=%{http_code} dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://clip.example.com/healthz
   ping -c 20 10.66.0.2
   ```

3. **用户实际公网路径**：在用户设备执行同一个 curl，去掉 `--resolve`，并分别从家中和外网测试。Windows 用 `curl.exe` 和 `-o NUL`。计时字段为自请求开始的累计秒数；TTFB 含 DNS、建连和 TLS，不能直接当作服务端执行时间。不同出发点的结果也不能机械相减。

4. **浏览器 Network**：查看 `/api/items/text`、`/api/events`、随后 `/api/items`、`/preview` 的大小、协议、排队和等待。发送完成耗时与对端出现消息耗时分别记录。重点确认是否重复加载原图/PDF、列表是否很大，以及下载时小请求的等待是否同步上升。

5. **吞吐与拥塞**：用专门测试文件测用户下载速度，再通过 WireGuard 内的临时 iperf3 测公网服务器与家中双向吞吐，观察云出口带宽图、家中上行和 TCP 重传。只在隧道接口开放测速监听；不要为测速更改现有公开入口或读取私人文件。若大传输时 RTT 明显上升，测量后考虑在实际瓶颈处整形并给交互流量留余量。

判断：家中本地就慢，先查磁盘/CPU/数据库；本地快而隧道慢，查两端带宽、路由、丢包和必要时 MTU；隧道快而用户公网慢，查入口出口和用户到入口线路；所有小接口快而 UI 慢，重点处理重复刷新、缩略图和浏览器渲染。

## 推荐实施顺序与架构选择

**第一步：应用侧减少无用流量。** 优先真正的图片/PDF 缩略图、POST 成功立即更新、SSE 增量更新与刷新去重。这些改动对保留现有架构也有效。缩略图生成用后台任务，结果沿用原文件权限和生命周期；完整列表保留作重连恢复。分别测优化前后的发送确认、另一设备收到、图片/PDF 首屏和下载速度。

**第二步：按使用场景消除绕行。**

| 使用场景 | 方案 | 条件与影响 |
| --- | --- | --- |
| 主要在同一家中局域网 | 相同 HTTPS 域名在局域网解析到家中 Caddy | 需要给 Caddy 增加受控的局域网监听；现有 Compose 只绑定隧道 IP，单改 DNS 不够。远程访问仍保留公网入口 |
| 主要是自己的几台设备 | Tailscale 或自建直连 WireGuard 到家中 HTTPS 服务 | 每台设备需安装和配置客户端，仍受家中上行限制；保留证书、域名和权限校验 |
| 必须任意浏览器直接打开，且数据留家中 | 优化或更换公网中转链路，购买带宽前先测实际两段路径 | 保留现有存储与 TLS 模型；仅给中转升带宽无法修复较慢的家庭上行或跨境线路 |
| 可以把数据放云上 | 把应用与存储一起放到合适的公网节点 | 去掉公网节点到家中的在线依赖，但改变数据存放位置。只迁前端或只加 CDN，API/文件仍回家中则不会根治 |

Tailscale 需要通过 `tailscale ping`/`tailscale status` 确认确实是 direct；打洞失败仍会走 DERP 等中转，并非安装后必然提速。[Tailscale 连接类型官方文档](https://tailscale.com/docs/reference/connection-types)

若以后需要对象存储直传/直下载，应单独设计权限校验、短期签名 URL、Range/CORS 和生命周期；这是改变数据路径的后续架构选项，并非本次诊断已经实施的方案。

要确定生产主因及其占比，还需要：实际域名、公网入口带宽、家中所在地与上行、访问者所在地，以及空闲时文字发送是否仍慢。先测再决定是否购买带宽或搬迁节点。
